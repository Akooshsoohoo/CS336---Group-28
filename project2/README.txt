3. Design Summary
-------------------
23 tables:
- application (main table, 349,563 rows). Only integer codes plus
  respondent_id (text). location_id is the only location column in it.
- 14 code/name lookup tables: agency, loan_type, property_type, loan_purpose,
  owner_occupancy, preapproval, action_taken, purchaser_type, hoepa_status,
  lien_status, ethnicity, sex, race, denial_reason. ethnicity, sex and race
  are shared by applicant and co-applicant.
- 4 location tables: location (2,135 rows, key location_id), state (1 row,
  NJ), county (21 rows, key state_code + county_code), msamd (11 rows).
  location has a UNIQUE constraint over all 10 location columns, so every
  location appears once. NULLs count as equal (NULLS NOT DISTINCT).
- 3 join tables for 1st normal form, each with a number column that says
  which race / reason it was:
    applicant_race     (sequence_number, race_number 1-5, applicant_race)      351,510 rows
    co_applicant_race  (sequence_number, race_number 1-5, co_applicant_race)   350,201 rows
    application_denial (sequence_number, denial_reason_number 1-3, denial_reason)  45,088 rows
- all_null_columns: one row (id = 1) holding edit_status, edit_status_name and
  application_date_indicator, which are blank in every row. A CHECK keeps them NULL.
  (sequence_number in the CSV is also blank, so the export writes ''.)

Error checking (Step 4): every code column is a foreign key to its lookup
table, so a bad code such as property_type 4 is rejected. Columns that are
never NULL in the data are NOT NULL. Primary keys stop duplicate ids,
CHECKs limit race_number to 1-5 and denial_reason_number to 1-3, and the
composite key (state_code, county_code) is a foreign key from location.


4. Development Challenges & Time Spent
------------------------------------------
- Matching each Preliminary row to its location is hard because "=" does
  not match NULLs, and a NULL-safe join was far too slow. We join on one
  text key per row built with concat_ws (NULL becomes '~'), which Postgres
  can hash-join.
- Foreign keys are added after the bulk load. Checking them row by row
  during the insert hit the server timeout.
- application.sequence_number is GENERATED BY DEFAULT AS IDENTITY, loaded with
  the original numbers, and the sequence is then moved past the maximum so
  new inserts get fresh numbers.
- The export needs LEFT JOINs (5 race slots x 2, 3 denial slots) to put the
  join-table rows back into columns. rate_spread is re-padded with
  to_char(..., 'FM00.00') as in Project 1.
- all_null_columns is CROSS JOINed in the export, so it must always hold
  exactly one row. It has a constant primary key id (CHECK id = 1) so a
  second row is rejected, and a trigger blocks DELETE and TRUNCATE.
- Time spent: about 4.5 hours (Akash) on the SQL scripts, testing on ilab,
  the videos and this README.
